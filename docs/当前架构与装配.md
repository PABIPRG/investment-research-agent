# V1.4 架构与当前实现映射

更新：2026-10-30（第 3 节补清 DSH/火火代码所有权边界；业务设计不变）。**按用户确认，策略后台已收敛到原 V1.4 的委托核心与统一执行链。** 策略计划采用类型化委托保存范围、版本与取消代次；计算与 DSH 候选共用 research_jobs、execution/attempt、租约和恢复。策略规则、模拟验证和候选仍属侧车研究领域；DSH、通知与 distribution 的责任不转移。运行证据与限制见第 6 节及统一实施记录。

先读 [团队 Brief](设计基线/V1.4-团队Brief.md)，需要完整契约时读 [V1.4 设计基线](设计基线/V1.4-产品与架构设计.md) 与 [V0.2 实施计划](设计基线/V0.2-能力接入实施计划.md)。本页前两张图逐字承接团队 Brief；后三张补充当前工程装配、Skill 调用与后台控制细节。目标、代码存在和验收通过分别说明。

这是一张逻辑职责图。研究、委托核心、投资事实、通知分别持有自己的正式数据；同一 SQLite 实例不改变其领域所有权。模块不要求与 Plugin、Bundle、包或进程一一对应。

- **DSH**：理解、澄清、规划、工具选择、跨材料推理和解释；提交业务命令、结果、证据引用与联系建议。
- **委托核心**：保存生命周期、版本、依赖、业务任务、条件和正式联系决定；模型建议不是发送许可。
- **通知**：消费获准联系意图，处理渠道、静默、去重、投递、重试和回执；发送前再次核验资格。
- **研究与投资事实**：分别保存身份/范围/证据、持仓/自选/成交/修订；事实修订可影响委托，但不自行扩大用户授权。

研究对象关系回答“对象之间有什么关系”；委托依赖关系回答“哪些变化需要唤醒哪项研究”。二者通过稳定标识连接，不因此引入图数据库或第二套状态。

| ② 火火接入层 | Profile/Bundle 配置；UI、Tool、Skill、guard 插件；把领域能力接到 DSH | Profile 是运行配置；Tool 是受控能力接口；Skill 是方法。接入层不维护第二份委托或持仓状态 | [product](../product/)、[聊天 Profile 装配](../distribution/chat.ts)、[worker Profile 装配](../distribution/instance.ts)、[策略 Profile 装配](../distribution/strategy-profile.ts) |
| ③ 火火业务内核 | 正式业务数据、版本/代次、job/attempt/lease、证据准入、确定性条件、联系决定和可靠通知 | Python 提供有界资料、计算和业务命令，不运行第二套自由规划 Agent；模型建议经程序验证后才能生效 | [sidecar](../sidecar/huohuo/)、[委托装配](../sidecar/huohuo/mandates.py)、[执行台账](../sidecar/huohuo/execution.py) |
| ④ 火火运行管理 | 产品安装、实例、环境、版本及进程生命周期；后台 worker 驱动一次业务执行 | worker 管业务执行交接与租约；需要模型时调用 DSH SDK。安装与启停管理不参与投资判断 | [distribution](../distribution/)、[runtime](../runtime/)、[研究 worker](../distribution/worker.ts)、[策略执行驱动](../distribution/strategy-worker.ts) |

有两条不同的调用路径：前台由 DSH 原生聊天结合火火插件执行；后台由火火 worker 领取业务任务，通过官方 `HarnessClient` 创建 DSH 运行、提交 prompt 并接收事件/结果，再回写业务台账。`huohuo-worker` 和 `huohuo-strategy-worker` 都复用 DSH 的 Agent 能力，按各自权限集合运行，不是火火另外实现的两种 Agent 内核。

页面可以直接调用受控业务接口，不必经过聊天 Skill；聊天和页面共享同一领域状态。普通后台研究只允许 `read_security_snapshot`；策略候选 Profile 禁用工具，只提交结构化候选。候选保存、策略启用和预案应用仍由侧车核验用户确认。纯价格条件和直接到期提醒按程序分流，已有确定性任务不因为架构图中画出 DSH 就强制调用模型。

图中将委托、研究、投资事实、策略和通知折叠为“受控 API 与领域服务”以突出 DSH/火火边界；各领域仍各自拥有状态，具体职责见第 2 节。联系决定属于委托核心，发送许可与回执属于通知领域，不能因合框转移职责。DSH 会话存储与实例业务 SQLite 分开；会话文本不替代业务库，业务库也不承担 DSH 会话引擎。

策略后台不再拥有另一套任务或租约。计划经用户确认后形成 `strategy_validation` 类型委托；按类型分派计算或受限 DSH 候选。两个资源消费者使用相同的 claim、heartbeat、runtime、recover 与执行台账。策略结果按自身语义接收，不生成证券研究基准、不产生联系决定，也不直接外发通知。旧独立表只读归档，不能继续调度。

产品仍是一个主要 npm 包加同版 tgz；内部 chat bundle/UI 包不是独立对外发行物。已有兼容 DSH 接入与从零安装仍是两条目标路径；当前受控 Profile 安装证据不能替代外部 DSH 兼容验收。

## 4. 按需 Skill：接入层内的局部变化

![DSH 按任务选择方法与工具](architecture/skills.svg)

能力继承分支当前已整合 5 个聊天 Skill，名称及 107 个 Tool 以 [能力目录](Skill与Tool能力目录.md) 为准，运行时名单由 policy 和 guard 维护。风险偏好问卷复用投资档案的版本、审计和确认回执，只作研究背景，不改变委托／通知或触发持仓事件。

<!-- diagram: skills -->
```mermaid
flowchart TB
  input["用户表达 + 可信上下文"] --> agent["DSH Agent<br/>常驻不变量、Skill 摘要目录、工具 schema"]
  agent -->|"无需工具即可回答"| answer["回答<br/>区分事实、推断、未知与实际回执"]
  agent -->|"需要方法正文"| skillguard["聊天 guard<br/>工具白名单 + Skill 名称/参数限制"]
  skillguard --> loader["DSH 原生 skill loader<br/>仅包内五个产品 Skill"]
  loader -->|"正文进入上下文；可加载多个"| agent
  agent -->|"需要业务读写"| toolguard["聊天 guard<br/>允许的工具名称"]
  toolguard --> bridge["工具桥<br/>参数、可信会话、幂等请求键"]
  bridge --> api["sidecar 业务校验<br/>主体、确认回执、授权、版本、证据"]
  api -->|"业务事实与持久回执"| agent
  skillguard -->|"不允许"| rejected["拒绝并返回错误<br/>不执行所请求能力"]
  toolguard -->|"不允许"| rejected
  rejected --> agent
```

这里画的是可选调用路径，**不是程序强制的“每次先加载 Skill 再调业务工具”流水线**。模型按任务选方法；后端授权不依赖是否加载或遵守 Skill。

| 层 | 实际责任 | 不承担的责任 |
|---|---|---|
| 常驻 policy 与五个 Skills | 不变量、研究、委托、投资事实、通知、策略方法 | 不产生主体身份、确认回执或发送许可 |
| DSH 原生目录与 loader | 发现产品方法，按需读取正文；关闭 home/cwd 扫描 | 不授权读取任意文件，不改变业务状态 |
| 聊天 guard | 现有工具白名单；本轮增加 Skill 名称与参数白名单 | 不负责全部会话权限、租约或正式业务状态 |
| 工具桥 | 参数、可信会话、callId、幂等键与 API 适配 | 不取代后端事务校验 |
| 各领域与执行 API | 身份、确认、权限、版本/取消代次、租约、证据、持久化 | 不运行第二套 Agent |

研究方法中的报告期、指标、单位、basis 与证据语义保留；原生 Skill 本身不是授权回执。原48项加主分支18项，共67项资料研究定义中63项生效，其余由正式业务入口替代；另有2个结构化研究审查 Tool 复用研究调用台账保存 DSH 原建议、九视角摘要、画像版本和确定性校准结果；原文、证据与未知分别保留。schema 常驻，没有工具延迟加载。上下文字节变化不等于 token、费用或研究质量已经改善。

## 5. 后台控制：持久流程中的分支

以下是**统一后台链路**与 V1.4 约定的对应图，包含策略类型分派。本图表达流程分支，代码所有权与 DSH/火火边界见第 3 节；图中的 DSH 节点均指调用上游 Agent 能力。真实资料、渠道与恢复矩阵仍需验收。通知异常分支只说明资格与回执语义，不覆盖所有错误码。

```mermaid
  wait -.->|"新事件或到期重评"| event
```

`mandate_id + mandate_revision + cancel_generation → job_id → execution_id → attempt_id` 保持绑定。初次研究通过持久事件路由。本轮已补成功基准门禁：语义变化复核缺少基准时等待；明确绝对数值条件、到期提醒与定时交付按自身契约执行，不强制套用比较基准。内容哈希不冒充发布时间。`met / unmet / unknown / error` 分别保存，未知不折叠成未满足。联系决定属于委托核心，通知只负责可靠交接与投递。accepted 仅受理，应用内 delivered 不等于外部送达、用户已读或采纳。
