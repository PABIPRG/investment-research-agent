# V1.4 架构与当前实现映射

更新：2026-10-26。**V1.4 的产品与业务架构保持有效。本轮按需 Skill 和 guard 调整属于产品接入层内部变化，不构成新的业务架构版本。**

先读 [团队 Brief](设计基线/V1.4-团队Brief.md)，需要完整契约时读 [V1.4 设计基线](设计基线/V1.4-产品与架构设计.md) 与 [V0.2 实施计划](设计基线/V0.2-能力接入实施计划.md)。本页前两张图逐字承接团队 Brief；后三张补充当前工程装配、Skill 调用与后台控制细节。目标、代码存在和验收通过分别说明。

![V1.4 业务职责与交互](architecture/business-architecture.svg)

```mermaid
    RESEARCH <--> STORE

    NOTICE <--> STORE
```

这是一张逻辑职责图。研究、委托核心、投资事实、通知分别持有自己的正式数据；同一 SQLite 实例不改变其领域所有权。模块不要求与 Plugin、Bundle、包或进程一一对应。

- **DSH**：理解、澄清、规划、工具选择、跨材料推理和解释；提交业务命令、结果、证据引用与联系建议。
- **委托核心**：保存生命周期、版本、依赖、业务任务、条件和正式联系决定；模型建议不是发送许可。
- **通知**：消费获准联系意图，处理渠道、静默、去重、投递、重试和回执；发送前再次核验资格。
- **研究与投资事实**：分别保存身份/范围/证据、持仓/自选/成交/修订；事实修订可影响委托，但不自行扩大用户授权。

研究对象关系回答“对象之间有什么关系”；委托依赖关系回答“哪些变化需要唤醒哪项研究”。二者通过稳定标识连接，不因此引入图数据库或第二套状态。

## 3. 当前运行装配：业务职责落在哪里

以下是工程视图，补充第 2 节，不取代业务架构。`distribution` 管启动与停止，不位于投资判断流程上游。

![当前运行装配与持久状态](architecture/ownership.svg)

<!-- diagram: ownership -->
```mermaid
flowchart TB
  life["distribution<br/>安装、实例、产品进程生命周期"]
  chat["huohuo-chat Profile<br/>交互式 DSH Agent"]
  worker["后台 worker<br/>领取、续租、结果回写"]
  sdk["huohuo-worker Profile<br/>一次 DSH 研究"]
  ui["product/ui<br/>委托、投资事实、消推页面"]
  tools["product/chat<br/>工具桥与聊天 guard"]
  bounded["product/tools<br/>read_security_snapshot"]
  api["sidecar API<br/>身份、权限与业务接口"]
  domains["sidecar 各领域<br/>研究 / 委托核心 / 投资事实 / 通知"]
  db[("实例 SQLite<br/>各领域正式状态")]
  sessions[("DSH 会话与模型配置<br/>与业务库分别持久化")]
  life -.->|"管理进程"| chat
  life -.->|"管理进程"| worker
  life -.->|"管理进程"| api
  chat <-->|"对话与工具调用"| tools
  chat <--> sessions
  ui <-->|"受控 Host 接口"| api
  tools <-->|"业务命令与查询"| api
  worker -->|"启动一次执行"| sdk
  sdk <-->|"本次 Scope"| bounded
  bounded <-->|"有界研究"| api
  worker <-->|"发现、领取、续租、回写"| api
  api <--> domains
  domains <--> db
```

页面可以直接调用受控业务接口，不必经过聊天 Skill；聊天和页面最终共享同一领域状态。两个 Profile 是运行场景，不是两套业务所有者。Python 提供有界数据、计算和业务服务，不启动第二个自由规划 Agent。worker 当前只允许 `read_security_snapshot`，禁用 subagent 和任意执行；这是当前后台适配范围，不是 V1.4 对全部研究能力的最终上限。

产品仍是一个主要 npm 包加同版 tgz；内部 chat bundle/UI 包不是独立对外发行物。已有兼容 DSH 接入与从零安装仍是两条目标路径；当前受控 Profile 安装证据不能替代外部 DSH 兼容验收。

## 4. 按需 Skill：接入层内的局部变化

![DSH 按任务选择方法与工具](architecture/skills.svg)

图为初始装配快照（3 个聊天 Skill）；本轮新增通知 Skill 后为 4 个，当前名称及工具数量以 [能力目录](Skill与Tool能力目录.md) 为准，运行时名单由 policy 和 guard 维护。

<!-- diagram: skills -->
```mermaid
flowchart TB
  input["用户表达 + 可信上下文"] --> agent["DSH Agent<br/>常驻不变量、Skill 摘要目录、工具 schema"]
  agent -->|"无需工具即可回答"| answer["回答<br/>区分事实、推断、未知与实际回执"]
  agent -->|"需要方法正文"| skillguard["聊天 guard<br/>工具白名单 + Skill 名称/参数限制"]
  skillguard --> loader["DSH 原生 skill loader<br/>仅包内三个产品 Skill"]
  loader -->|"正文进入上下文；可加载多个"| agent
  agent -->|"需要业务读写"| toolguard["聊天 guard<br/>允许的工具名称"]
  toolguard --> bridge["工具桥<br/>参数、可信会话、幂等请求键"]
  bridge --> api["sidecar 业务校验<br/>主体、确认回执、授权、版本、证据"]
  api -->|"业务事实与持久回执"| agent
  skillguard -->|"不允许"| rejected["拒绝并返回错误<br/>不执行所请求能力"]
  toolguard -->|"不允许"| rejected
  rejected --> agent
```

这里画的是可选调用路径，**不是程序强制的“每次先加载 Skill 再调业务工具”流水线**。模型按任务选方法；后端授权不依赖是否加载或遵守 Skill。

| 层 | 实际责任 | 不承担的责任 |
|---|---|---|
| 常驻 policy 与四个 Skills | 不变量、研究方法、委托操作方法、投资事实表达、通知偏好 | 不产生主体身份、确认回执或发送许可 |
| DSH 原生目录与 loader | 发现产品方法，按需读取正文；关闭 home/cwd 扫描 | 不授权读取任意文件，不改变业务状态 |
| 聊天 guard | 现有工具白名单；本轮增加 Skill 名称与参数白名单 | 不负责全部会话权限、租约或正式业务状态 |
| 工具桥 | 参数、可信会话、callId、幂等键与 API 适配 | 不取代后端事务校验 |
| 各领域与执行 API | 身份、确认、权限、版本/取消代次、租约、证据、持久化 | 不运行第二套 Agent |

研究方法中的报告期、指标、单位、basis 与证据语义保留；原生 Skill 本身不是授权回执。66 项研究工具及其他业务工具的 schema 仍常驻，没有工具延迟加载。上下文字节变化不等于 token、费用或研究质量已经改善。

## 5. 后台控制：持久流程中的分支

以下是当前控制结构与 V1.4 约定的对应图，真实资料、渠道与恢复矩阵仍需验收。通知异常分支只说明资格与回执语义，不覆盖所有错误码。

![后台执行、静默与可靠投递](architecture/background.svg)

<!-- diagram: background -->
```mermaid
flowchart TB
  event["委托命令 / 资料版本 / 时间事件"] --> inbox["持久 outbox / inbox"]
  inbox --> route{"当前委托有效并命中依赖？"}
  route -->|"否"| wait["保留记录，等待下一事件"]
  route -->|"是"| kind{"业务任务类型"}
  kind -->|"到期提醒"| reminder["程序核对到期与有效约定<br/>无需额外模型研究"]
  kind -->|"初次研究 / 后续复核 / 成果交付"| ready{"后续复核且初次研究<br/>仍在排队或运行？"}
  ready -->|"是：等待进行中的初次研究"| wait
  ready -->|"否：当前门禁允许继续"| exec["job → execution / attempt / lease"]
  exec --> dsh["DSH 调用有界能力<br/>返回结果与证据引用"]
  dsh --> admit{"主体、范围、版本、attempt、证据有效？"}
  admit -->|"否"| invalid["失败 / 失效 / 缺口<br/>不冒充成功结果"]
  admit -->|"是"| result["保存基准或复核结果<br/>按任务类型处理"]
  result --> decide["委托核心<br/>核验约定、结果与四值条件，保存联系决定"]
  reminder --> decide
  decide -->|"不联系 / 条件未知 / 等待"| wait
  decide -->|"可联系或静默延期"| queue["通知：渠道、静默、队列、去重"]
  queue --> gate{"发送前事务复核<br/>版本、暂停、代次、渠道与时效"}
  gate -->|"过期 / 撤销 / 不允许"| invalid
  gate -->|"尚在静默期"| deferred["同一通知队列延期<br/>等待 eligible_at"]
  deferred -->|"到期后重新核验原队列"| gate
  gate -->|"许可"| send["持发送许可执行投递"]
  send --> receipt{"投递结果"}
  receipt -->|"已送达"| visit["携原委托入口回访<br/>继续对话或调整委托"]
  receipt -->|"accepted"| accepted["渠道已受理，送达未确认<br/>保存受理回执"]
  receipt -->|"不可重试失败"| failed["保存投递失败终态"]
  receipt -->|"明确可重试失败"| retry["按既定策略重试并再次核验"]
  retry --> queue
  receipt -->|"unknown"| reconcile["保留未知并对账<br/>不自动重发"]
  visit --> event
  wait -.->|"新事件或到期重评"| event
```

`mandate_id + mandate_revision + cancel_generation → job_id → execution_id → attempt_id` 保持绑定。初次研究通过持久事件路由。**V1.4 要求先有成功基准再复核；当前派发门禁会同时检查同版本 pending/running 的初次研究、以及 `mandate_progress` 中非空且版本匹配的基准，缺失成功基准时不派发事件复核。** 基准研究失败会按 `max_attempts`（默认 3）新建退避重试任务；重试用尽后该版本保持无基准，不伪造结论。内容哈希不冒充发布时间。`met / unmet / unknown / error` 分别保存，未知不折叠成未满足。联系决定属于委托核心，通知只负责可靠交接与投递。accepted 仅受理，应用内 delivered 不等于外部送达、用户已读或采纳。

## 6. 目标、当前代码与验证范围

| 能力 | V1.4 目标与当前代码事实 | 当前证据 / 仍缺什么 |
|---|---|---|
| 四入口与同一业务状态 | 目标四入口不变；当前已有相应页面和领域接入 | 本轮浏览器仅覆盖所记录的研究/委托关键链路，非全部 UI 验收 |
| DSH 与研究能力 | DSH 完整 Agent；聊天可见 66 研究工具，后台为有界单工具适配 | 原生受控回放通过；真模型、真资料质量与工具覆盖未完成 |
| 正式委托与联系约定 | 已有确认、生命周期与持久状态；create/revise 可保存单个显式语义联系条件（claim + 必须有证据 + 可选置信度），不填写时仍为 notable_change；报价类委托另可保存用户明确说出的单点数值阈值（price/change/change_percent + operator + threshold） | 自然语言并非任意编译：只接受用户明确说出、可举证的单一条件；数值条件的取数由程序从本次绑定的报价快照读取，模型自报数字不参与判定；均线、回撤、分位等需要历史序列的条件仍直接拒绝 |
| 资料发现 | worker 已调用 discover；自动发现覆盖财务摘要（30 分钟）、公司资料（6 小时）与报价（沪深交易时段内每 15 分钟，按价格字段版本判定变化）的内容版本，实际可用性以实例记录为准 | 不能说完全没有发现代码；也不能以轮询函数存在证明完整真实持续监测。报价每次价格变化都会产生一次复核任务（盘中约每日十余次），成本需按实例记录评估；来源失败不视为无变化 |
| 后续复核的基准前置 | 派发前要求同版本成功基准；基准失败按 max_attempts 退避重试，重试用尽不再派发复核 | 失败路径已有回归测试；中断后租约过期路径由 lease 测试覆盖，未新增专门用例 |
| 联系与通知 | 核心决定、队列、发送前复核和回执代码已存在；通知默认关闭 | 受控/零外发证据不能证明真实外部渠道送达 |
| 安装与发行 | 独立根历史、一个主包；已有受控仓外安装与启动证据 | 外部 DSH 复用、双路径全验收、跨平台、迁移/回滚和公开发布仍待完成 |

当前实现细节并不反向删减 V1.4 目标；历史 Brief 的“尚未实现”也不覆盖之后出现的代码。状态以 [交付与验收](交付与验收.md) 的对应日期、产物和证据为准，完整 M1/M2 保持未完成。

本次调整原因、代码核查与验证记录见 [架构对齐记录](架构对齐与验证.md)。设计演进原图保留在团队 Brief，没有把按需 Skill 描述成 V1.5 或新的领域拆分。
