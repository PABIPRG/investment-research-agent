## 1. 现在如何运行

当前实现分为两次独立的程序判断：委托核心根据用户约定、当前状态和研究证据决定是否联系；通知模块取得这个决定后，根据当前配置、静默、时效和渠道状态决定能否开始投递。DSH 提供研究结果和建议，不能直接签发发送许可。

```text
明确的持续委托 + 已确认范围/联系规则
  → 时间或资料事件 → 持久事件路由 → 业务 job
  → 到期提醒：程序处理
    纯价格条件：程序价格执行器（仍绑定 execution/attempt）
    其他研究：准入门禁 → DSH → 本次结果和证据
  → 委托核心 ContactDecisionService：联系决定
  → Notifications.enqueue：按决定和渠道持久入队
  → Notifications.reserve：发送前事务复核 → permit / in_flight
  → 应用内留存，或企业微信 / Server 酱 / SMTP
  → settle：受理、送达、失败、重试或未知
```

此处是代码调用顺序，业务主图继续使用[当前架构](当前架构与装配.md)中的 V1.4 Mermaid 与派生 SVG，不另建架构图源。

普通讨论、确认对象、加入自选、保存渠道配置均不自动创建持续委托或扩大渠道授权。全局提醒默认关闭；默认渠道为 `app`。后台运行依赖产品 worker 和侧车保持运行，主机休眠或进程停止会中断执行。

一个需要特别审核的运行限制：通知消费挂在 `Mandates.tick()` 末尾，而该 tick 由研究 lane 的 `/worker/claim` 请求驱动。[workerLoop](../distribution/worker.ts) 先 recover、discover、claim，再等待一次研究结束；空闲时约 500ms 再轮询，异常时约 5 秒退避。当前不是独立通知调度进程，因此不能承诺严格 500ms 的通知时延；资料发现或研究耗时也会影响队列再次被消费的时间。

## 2. 核心如何决定联系

| 检查 | 当前实现 | 审核入口 |
|---|---|---|
| 规则从哪里来 | `contact_rule` 编译成可执行 policy，随委托 revision 保存；自由文本备注不直接成为执行规则 | [contact_rules.py](../sidecar/huohuo/research_partner/contact_rules.py)、[Mandates.create/command](../sidecar/huohuo/mandates.py) |
| 委托是否仍有效 | 核对 tracking、当前 revision、结果 stale、持仓风险计划资格；迟到或失效结果只留档 | [contact.py 的 _decide](../sidecar/huohuo/research_partner/contact.py)、[receive_results](../sidecar/huohuo/mandates.py) |
| 条件是什么 | `met / unmet / unknown / error` 分别保存；单位、数据口径、证据不足不折叠成满足 | [conditions.py](../sidecar/huohuo/research_partner/conditions.py) |
| 联系时机 | 支持 `condition`、`periodic_check`、`scheduled_delivery`、`due_reminder`；定时模式要求相符的到期 action，首次研究不能替代到期事件 | [contact_policy.py](../sidecar/huohuo/research_partner/contact_policy.py)、[contact.py](../sidecar/huohuo/research_partner/contact.py) |
| 是否重复满足 | 根据 `notify_on`、持续时长和已存条件状态处理；unknown/error 不写成离开条件 | [contact.py 的 _apply_state_gate](../sidecar/huohuo/research_partner/contact.py) |
| 是否暂缓或降噪 | 按暂缓、冷却、合并窗口和静默生成 `suppress / aggregate / defer / send` 决定 | [contact.py 的 _suppress_or_send](../sidecar/huohuo/research_partner/contact.py) |

明确到期提醒由 `complete_reminder()` 生成“按约到期”的结果，跳过 DSH，不虚构新的研究结论。纯价格规则走[程序价格执行器](../sidecar/huohuo/research_partner/price_execution.py)；其他研究是否调用模型由[准入门禁](../sidecar/huohuo/research_partner/model_admission.py)和 worker 共同控制。

需要比较基准的语义复核在成功基准前等待；绝对数值阈值、直接到期提醒、定时成果按各自规则执行，不能一概要求新增模型研究。资料事件命中只代表可进入后续程序核验，不代表已经达到联系条件。

`condition_unknown` 的等待属于核心复核；通知 `unknown` 表示外发结果不确定，两者不能混用。核心 `_schedule_retry()` 还要求预算、期限及重试次数允许；当前常规规则编译设置 `max_retries=0`，不能把保存了 `eligible_at` 解释成一定会追加模型研究。

最新主线还增加了[通知优先级](../sidecar/huohuo/notifications/priority.py)、[研究任务排序](../sidecar/huohuo/research_partner/research_priority.py)、合并窗口展示锚点和可选语义证据置信度校准。通知/任务分数决定同样合格项的先后，不授予发送或研究许可；语义校准在显式配置开启时保守降低置信度，可能使证据不足的结论保持 unknown，不将 unknown 折叠成 unmet。完整边界见[消推算法第 13 节](消推算法.md#13-排序与校准打分不参与放行)。

核心中保留可选旧 dispatcher 接口，但新装配调用 `ContactDecisionService(self.store)`，不传 dispatcher。正式通知出口是下面的持久队列；旧接口存在不能推导旧直推仍在新产品运行。

## 3. 从决定到队列的可靠交接

[Mandates.tick / receive_results / complete_reminder](../sidecar/huohuo/mandates.py) 在同库事务中接收结果、保存联系决定、调用 `Notifications.enqueue()` 并更新回执。插入队列失败会回滚本轮接收，不留下“决定已保存但交接丢失”的成功状态；网络投递在该事务提交之后进行。

只有 `send` 和 `defer + quiet_hours` 能入通知队列。`condition_unknown`、冷却、暂缓及合并决定不会由通知模块自行复核成发送。入队渠道取“委托 policy 渠道 ∩ 当前配置启用渠道 ∩ 已支持渠道”。

持久去重分三层：

- 核心按委托和 `job:<job_id>` 保存唯一联系决定。
- 队列以 `(decision_id, channel)` 为主键，`INSERT OR IGNORE` 防止重复入队；同一决定的各渠道分别记录状态。
- 一次发送领取生成 `permit_id`；回写按决定、渠道和 permit 匹配，过时回执不能覆盖其他许可。

实际持久表见 [008 迁移](../sidecar/huohuo/research_partner/migrations/008_followup_notifications.sql)、[009 迁移](../sidecar/huohuo/research_partner/migrations/009_notification_channels.sql)、[020 测试记录](../sidecar/huohuo/research_partner/migrations/020_notification_tests.sql)、[021 通知排序](../sidecar/huohuo/research_partner/migrations/021_notification_priority.sql)、[022 任务排序](../sidecar/huohuo/research_partner/migrations/022_research_job_priority.sql)及[联系决定存储](../sidecar/huohuo/research_partner/adapters/sqlite_store.py)：

| 状态所有者 | 数据 |
|---|---|
| 委托核心 | 委托及 revision/generation、research_jobs/results、contact_decisions、条件状态 |
| 通知偏好与配置 | notification_preferences、notification_config、notification_channels、notification_config_audit |
| 投递状态与历史 | notification_queue、notification_receipts |
| 手动渠道测试 | notification_tests；不生成正式委托、联系决定或业务通知队列 |

它们在同一实例 SQLite 中，但职责不同。`notification_queue` 是持久投递交接，不是另一套联系算法。凭据保存在实例数据库中；数据库权限设置为 `0600`，接口及配置审计脱敏，当前没有在该代码中实现凭据字段加密，备份也应按含秘密数据处理。

## 4. 发送前最后检查什么

[Notifications.reserve()](../sidecar/huohuo/notifications/service.py) 和暂停、改配置使用相同的 SQLite 写事务串行化；事务提交被定义为“发送起点”。只有尚未开始的 `queued / deferred / retry` 且到达 `eligible_at` 的任务可领取。

领取时逐项核对：

1. 委托仍在 tracking，revision 与取消 generation 匹配。
2. 联系许可没有过期；未指定到期时间时，入队默认 24 小时 TTL。
3. 全局提醒启用，当前渠道仍启用、仍在委托许可内。
4. 外部渠道配置仍完整，且配置 revision 与入队时一致；换密钥或目标后取消旧队列，等待新决定。
5. [市场资料门禁](../sidecar/huohuo/notifications/market_gate.py)允许新的发送：市场类范围重新核对触发版本、结果、attempt、证据与时效；直接到期提醒不要求新行情证据。
6. 如属持仓风险计划，重新核对该计划当前资格。
7. 按当前全局时区与静默时段重新计算延期；仍静默则更新同一队列的 `eligible_at`。

通过后写为 `in_flight`、增加 attempts 并生成 permit，随后才调用适配器。暂停先提交可阻止新的领取；permit 先提交则请求可能已在途中，后续暂停不能承诺撤回。程序不持数据库事务等待外部网络，也不承诺外部渠道绝对只送一次。

时效复核目前对 `MARKET_OPERATIONS` 做完整证据重验；`quote_snapshot / company_profile / financial_summary` 在该发送门禁中保留既有策略，不具备同等的发送时行情时效核查。不能将“发送前重验”概括成所有资料源均有相同检查深度。

## 5. 投递状态与重试

| 状态 | 当前含义与后续动作 |
|---|---|
| queued | 已入队，等到 eligible_at 后领取 |
| deferred | 仍在静默期，延期后重验当前资格；静默结束不会自动新增研究 |
| in_flight | 已取得 permit，外部请求可能正在执行 |
| accepted | 适配器已成功返回；渠道受理，终端送达未确认；不自动重发 |
| delivered | 当前 `app` 路径表示已保存到应用内回访；不代表用户已读，也不代表外部终端送达 |
| retry | 仅用于“确定未成功且明确可重试”的失败；按 `60 × attempts` 秒退避，最多三次领取，每次重新核验 |
| failed | 不可重试，或可重试次数达到上限 |
| unknown | 结果不确定，或 in_flight 超过 60 秒；不进入自动重发集合 |
| cancelled | 许可过期、委托/代次失效、渠道变化或发送门禁拒绝；不继续投递 |

`tick()` 只扫描到期的 queued/deferred/retry。网络异常、渠道返回不确定错误统一保守进入 unknown；已有企业微信、Server 酱及 SMTP 包装将其传输异常标为 `outcome_uncertain=True`，所以这些异常实际不会走自动 retry。适配器成功返回 `None` 统一记 accepted，不能把 HTTP/SMTP 成功当作用户已收到。

`settle()` 允许同一个 permit 的 unknown/accepted 在获得确定结果后更新，说明状态模型留有对账能力；当前 API 已有配置、投递列表、应用内投影及手动渠道测试，但没有完整的正式投递渠道结果查询、人工对账或重试工作流。in_flight 超时转 unknown 由 tick 直接更新队列，不新增一条 receipt；排查时需同时看队列 detail 和回执表。

队列消费按 `priority DESC, eligible_at ASC, decision_id, channel` 处理到期项，不按分数过滤发送集合；是否能发送仍由 `reserve()` 决定。通知列表则先按 priority，再按 eligible_at、updated_at 排序。

## 6. 渠道、配置与回访入口

| 渠道 | 当前实现 | 结果解释 |
|---|---|---|
| app | 侧车保存应用内投递状态 | delivered 表示可在应用中回查 |
| wecom | [企业微信机器人](../sidecar/huohuo/notifications/push/wecom.py)，显式 key | 成功映射 accepted |
| serverchan | [Server 酱](../sidecar/huohuo/notifications/push/serverchan.py)，显式 sendkey | 成功映射 accepted |
| email | [EmailAdapter](../sidecar/huohuo/notifications/channels.py)，SMTP + STARTTLS，默认 587 端口 | 成功映射 accepted；此处没有隐式 TLS/465 专用实现 |

[配置校验](../sidecar/huohuo/notifications/configuration.py)拒绝任意额外字段和完整推送 URL；空白秘密字段保留原值，`clear:true` 明确清除。保存采用 `expected_revision` 防止覆盖并发修改；渠道秘密不回显、不进入审计正文。全局启用渠道和委托允许渠道分别维护，已有委托不会因新增全局渠道而自动授权外发。

页面复用[通知桥](../product/ui/notification-bridge.ts)访问配置、投递、应用内投影及手动测试接口；侧车按已认证主体处理。[聊天工具](../product/chat/notification-tools.ts)提供 `read_notification_settings`、`list_notification_deliveries`、`update_notification_preferences`、`clear_notification_channel`，以及 `prepare_notification_test`、`send_notification_test`、`read_notification_tests`。偏好/清除写工具展示原值与变更并取得原生用户确认；测试发送由服务端读取已准备目标后取得原生确认。聊天不接收密钥或任意接收目标，新凭据由安全表单填写。

[确认式渠道测试](../sidecar/huohuo/notifications/testing.py)与正式通知分开：prepare 不发送，准备记录绑定主体、会话、请求和配置版本，5 分钟有效；send 再核对目标和总开关/渠道资格。测试明确忽略静默，但不绕过提醒总开关和渠道配置；只发送固定测试内容，不包含研究结论、不创建委托。重复/并发提交与未知结果不得盲重发。

外部消息当前附委托 ID、联系决定 ID、证据引用及回到应用的说明，没有可直接点击定位的外部消息深链接。浏览器 Web Push/设备订阅没有在本仓通知渠道中接入；应用内 delivered 也不是浏览器系统通知。投递列表返回当前主体按优先级和时间排序后的最多 200 条渠道记录，单委托视图再从这批记录过滤，不能当作完整通知审计导出。

`in_app()` 只投影其中已 delivered 的 app 通知，并加入最近 20 条 delivered 的应用内测试；前端[全局提醒层](../product/ui/reminders/store.ts)轮询该投影，按实例/主体 scope 在当前浏览器 origin 保存已见和待提示 ID，通过标签页所有权避免同时提示。它负责页面展示，不产生新的投递许可，也不等于跨设备已读回执。首次读取的历史记录不全部弹出，重开后的已存待提示记录按当前投影恢复。对应实施记录见[全局提醒与稳定刷新](设计基线/V1.4-全局提醒与稳定刷新.md)。

| 项目 | 已确认的代码事实 | 当前限制 / 审核意义 |
