## 5. 已复现但本次未修复的业务缺口

**初次研究失败后，基准为空仍可创建并领取后续复核 execution。** 这是来源已有的实现缺口，本次文档修正不能关闭它。

使用真实领域方法和独立 SQLite：合成实体解析/确认 → create → tick → claim → finish(failed) → Sources.accept 合成财务版本 → tick → claim。结果为 baseline 始终 null，执行数从 1 增到 2，第二个 event_review 已被领取为 running。没有直接 SQL 伪造业务状态，没有启动模型或服务、访问外部资料或发送通知；running 仅指隔离数据库中的领取状态。**本次只复现失败场景，中断场景未验证。**

定位：[mandates.py](../sidecar/huohuo/mandates.py) 的 pending/running baseline 门禁与随后 execution 创建，配合 [router.py](../sidecar/huohuo/research_partner/router.py) 的事件任务登记。局部报告为 artifacts/architecture-review/baseline-failure-reproduction.json，复现脚本同目录。V1.4 的成功基准前置目标继续有效，图第 5 节明确当前代码较弱的门禁。

后续关闭条件：明确无成功基准时业务任务等待/失败/重试的契约；修复前先保留该失败回归，再覆盖基准失败、中断、重试成功、旧版本/取消代次与提醒豁免。由持续研究实现负责人在宣称 M1 闭环之前完成。未擅自扩展本次为业务状态或调度变更，也未新建/改写外部事项。
